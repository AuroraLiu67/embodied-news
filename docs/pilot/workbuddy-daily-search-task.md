# WorkBuddy 国内科技动态每日候选搜索任务

## 1. 项目背景

我们正在建设“具身智能公司动态雷达（Embodied Intelligence Radar）”。

- WorkBuddy 负责国内公开网页、微信公众号生态和中文信源的候选发现。
- OpenAI 负责海外公开网络候选发现。
- 飞书多维表格是唯一正式数据源。
- WorkBuddy 只能提交研究候选，不能直接写飞书、创建正式事件、生成正式日报或决定发布。
- Codex 负责校验 WorkBuddy 输出、去重、导入飞书及后续工程流程。

## 2. 本次任务

使用同一 WorkBuddy 项目中提供的 `workbuddy-domestic-observation-list.md` 作为信源、赛道和补充查询参考，搜索以下业务日期发布的国内科技公司动态。Physical AI、具身智能及其上下游在候选排序中优先，但不是唯一收录范围：

**业务日期：`2026-08-03`，北京时间 `00:00–至今`。**

这是指定日期的历史试跑，不要把当前日期内容混入结果。以后每日运行时，只替换本节的业务日期，其他规则保持不变。

## 3. 搜索范围

按以下顺序执行：

1. 优先搜索观察清单中的 FA、VC/CVC、投资机构、36氪、投资界、专业财经媒体、科技与产业媒体及其公众号。
2. 如果搜索页面或已安装 Skill 支持，开启“最近一天”筛选，并使用观察清单 5.0 节的高命中事件词宽搜。
3. 融资、投资、并购、新产品、新技术、新模型、商业化、订单、交付、部署、量产、产线和工厂动态使用同一套发现与补充搜索逻辑。
4. 收录范围包括具身智能、视频生成、多模态与情绪交互模型、Agent、芯片与算力、光电、传感器、工业软件、新材料、能源和散热等科技与硬科技赛道。
5. 不在每日或每周任务中逐一检查重点公司，也不展开公司 × 赛道 × 事件的查询矩阵；只在发现具体线索后定向补搜该公司。
6. 每发现一条候选，继续搜索公司、事件参与方、融资金额和轮次、产品或合作对方及可用工商线索，补齐公司与赛道信息。

## 4. 内容类型

每条候选必须且只能选择一个类型：

- `FUNDING`：融资、并购、产业投资或其他明确资本事件。
- `TECHNOLOGY`：模型、算法、数据、仿真、关键技术或经过证据支持的能力进展。
- `PRODUCT`：新产品、产品发布、量产版本、关键零部件或产品升级。
- `COMMERCIALIZATION`：订单、交付、部署、客户合作、产线、收入或其他商业化进展。

某一类型没有合格结果时允许为空，不要为了填满四类而使用其他日期或低质量内容。

## 5. 日期与来源门禁

每条进入候选 JSON 的记录必须同时满足：

1. 来源页面明确显示发布时间属于指定北京时间业务日期。报道日期是每日归档依据；事件日期只在来源明确时记录，未披露时不得猜测。
2. 存在至少一个可直接打开的报道、公告或文章 URL。
3. 来源内容能够支持候选标题和摘要中的核心事实。
4. 内容属于有价值的科技公司、AI 或硬科技动态；Physical AI 相关内容在排序中优先。

来源与确认规则：

1. 公司、投资方、领投方、参投方、FA、客户、并购或合作参与方的正文明确确认，可标记为“已确认”。
2. 36氪、投资界及可靠专业财经媒体、科技媒体和产业媒体的原创报道是合格来源，不要因为没有公司官方公众号而筛除。
3. 其他有网址的第三方报道可进入候选，并按“多源佐证”“单源报道”或“待核验”保留当前证据状态。
4. 企查查、天眼查、爱企查和国家企业信用信息公示系统可用于辅助核验，但工商信息延迟、付费墙或无变更不影响候选收录。
5. 融资金额可为“数千万元”“数亿元”“近亿元”“亿元级”或未披露，均可正常收录；保留原文表述，不得猜测精确金额。

以下内容不能直接进入候选 JSON：

- 搜索结果页或搜索摘要。
- 日期不明确的文章。
- 没有任何可访问文章或公告网址的内容。
- 来源页面的发布日期不属于指定业务日的内容。
- 只有无法打开、登录后才可见或付费后才可见页面，且找不到任何可访问来源的内容。
- 只有传闻、概念炒作或无法由来源支持的判断。

日期待核验或仅作为搜索线索的结果，可以在任务总结中单独报告，但不要写入候选数组。

## 6. 去重与证据要求

- 相同 URL 被多个查询命中时合并为一条候选，并合并查询词。
- 同一事件被不同来源报道时可以保留不同来源线索，但不要把它们伪装成多个不同事件。
- 优先选择信息最完整、可访问且可支持核心事实的来源作为候选主 URL；找到参与方原文时作为交叉验证，不将其作为第三方媒体候选的强制前置条件。
- 不得根据常识、记忆或搜索摘要补齐金额、轮次、客户、产品参数或发布日期。
- 在 `preliminarySummary` 中简要补充公司所属赛道、公司做什么、核心产品/技术或应用场景，并标明当前证据状态；信息不足时写“待补充”。
- 不保存完整文章正文，只保留形成候选所需的简短摘要。

## 7. 输出契约

最终只生成一份符合项目 C01 `schemaVersion: "1"` 契约的候选 JSON：

`d05-workbuddy-candidates-2026-08-02.json`

具体字段、类型和长度限制以项目中的 `docs/workbuddy-candidate-format.md` 为准。输出前必须自行检查：

- JSON 可以被标准解析器解析。
- 顶层只有契约允许的字段。
- 每条候选的内容类型属于四个固定枚举之一。
- 每条候选都有合法原始 URL 和明确发布日期。
- 摘要没有完整复制原文。
- 相同 URL 没有重复记录。

WorkBuddy 不得生成或填写以下特权字段：

- `candidateId`
- `canonicalUrl`
- 审核状态
- 置信度最终评分
- 正式公司 ID、事件 ID 或动态 ID
- 日报 ID 或发布状态
- 是否公开
- 内部战投判断、投资建议或估值结论

如果没有任何合格候选，仍然输出符合 C01 契约的合法空 `candidates` 数组，不要编造内容。

## 8. 任务总结

除 JSON 产物外，只需提供一段简短总结，包含：

- 实际覆盖的公司、赛道和信源类别。
- 合格候选总数及四种内容类型的数量。
- 因日期不符、来源不合格、重复或相关性不足而拒绝的大致数量。
- 需要 Codex 或人工继续核验的线索。

不要在总结中粘贴完整网页正文、Cookie、Token、账号信息或平台内部数据。

## 9. 明确禁止

- 不直接调用飞书或修改飞书多维表格。
- 不生成正式融资事件、公司动态或日报。
- 不决定候选是否批准或允许公开。
- 不向飞书个人、群聊或其他外部渠道发送消息。
- 不修改观察清单本身；新对象只能作为“观察清单建议”交给 Codex 和用户审核。
- 不绕过任何平台访问控制。

完成后，将 JSON 文件保存为独立产物并交给用户。用户会把产物交给 Codex 做 Schema 校验、去重和受控导入。
